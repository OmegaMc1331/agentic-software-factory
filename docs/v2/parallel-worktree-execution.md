# Parallel worktree execution

Every implementation-family task uses the established `.factory/worktrees/t<ID>` and `factory/t<ID>` ownership model. Project/runtime and Git-common locks from P03 remain required. Dispatch claims associate project database, run, task, revision and owner; attempts retain worktree path, agent, attempt number and immutable source-base SHA. Concurrent task IDs are distinct; numeric collisions in other project databases do not share paths or claims.

Creation resolves the approved run branch to a commit SHA before calling Git. A sibling may start from the same immutable snapshot or a later published snapshot; both are recorded. A dependent can be claimed only after every predecessor publishes, and its new worktree therefore contains those predecessors. Evidence and retries use the recorded original task base, never a later mutable integration head.

ASF captures permitted Worker changes as a commit before review. This makes newly created files part of the actual bounded patch as well as modified tracked files. The existing scope/command checks and P07-R1 refusal classification run first. Reviewer receives the patch plus Rust-captured base/head and SHA-256 of the displayed patch. Truncation is explicit; captured facts do not assert tests passed and do not require granting Reviewer write access.

The Worker keeps the supported configured CLI sandbox, cwd and scoped MCP grant. Ordinary P05 manual editor access to active managed worktrees remains read-only. Application scopes are not an OS sandbox. Deny precedence, tool grants and publication permissions are unchanged.

Original task branches are retained. A rejected/conflicting candidate is preserved in a separate integration worktree. No force reset, force add, force checkout or side-selection merge strategy is used. Task worktrees, including successfully integrated task outputs, remain available for existing V1/P03 evidence inspection. Explicit maintenance remains responsible for their lifecycle; P08 does not delete their unreviewed modifications. The newest clean published integration snapshot is also retained for P05 read-only inspection. Older clean published candidates may be pruned only after checking their exact recorded HEAD and canonical containment within this project's integration directory; rejected, conflicted or dirty candidates remain preserved.
