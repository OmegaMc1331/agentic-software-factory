# Durable checkpoints and logical resume

Project migration 22 creates `workspace_session_lifecycle`, `mission_lifecycle`, `mission_checkpoints`, `lifecycle_commands` and bounded `workspace_session_events`. A schema-version-1 checkpoint binds project, workspace session, run and lifecycle generation. It references the committed plan revision, task/attempt identities and states, pending handoffs, integration commit, scoped worktrees and event cursor. Existing tables remain authoritative; checkpoint references do not create another task state store.

Git inspection occurs after owned execution stops and outside a SQLite write transaction. Each retained unfinished worktree records its original source base, actual HEAD and a fingerprint of tracked changes, Git status and bounded untracked file hashes. Symbolic links, reparse points, escaping paths and unregistered worktrees fail inspection. Checkpoint data stores hashes and identities, not source text, credentials, environment values or hidden reasoning. Creation then rechecks ownership/generation in a short immediate transaction, stores the checkpoint and emits its durable event. SUSPENDED follows only after this succeeds.

Limits are explicit: 256 checkpoints per run, 512 KiB per checkpoint and a 64 MiB project checkpoint budget. History is not silently deleted to satisfy the budget. Untracked inspection is limited to 256 files, 4 MiB each and 32 MiB total, with the existing bounded Git command output/deadline. Missing or oversized state becomes a visible recovery blocker.

Authenticated resume requires a current lease for the exact project/session, an open session and the expected lifecycle generation. It claims the next generation, checks the checkpoint schema/identity, current plan, task ownership, actual worktrees/commits, integration journal, external delivery state, current role/project policy, agent availability and pending handoffs. Publication uncertainty, denied policy, missing providers, archived profiles or changed worktrees do not authorize automatic replay. Provider quota refusals retain P08-R1 classification and stop ordinary recovery loops.

Only eligible remaining tasks are re-admitted through P08. Completed/integrated tasks keep their identities and publication records. Interrupted attempts retain their original history and partial work; a new bounded invocation reconstructs objectives, plan, source base, current files, prior results and review context. Suspension interruptions do not consume the code-quality retry budget once a validated managed checkpoint authorizes continuation. The overall active execution duration is accumulated across scheduler owners; suspension does not reset it. The checkpoint-retention bound also limits repeated recovery cycles.

Resume commit rechecks task states, plan revision and lifecycle generation transactionally. Duplicate commands cannot launch another owner. Current P09 profile revisions configure new invocations; older snapshots are never relabelled. A resumed mission is not restarted from an empty repository or a new top-level workflow.

Startup holds P03 ownership locks and uses existing P08 journal/session/claim reconciliation. Previously confirmed SUSPENDED missions stay fenced. Interrupted active/quiescing/resuming missions become recovery-required without automatic launch. An explicitly requested recovery verifies the recorded supervised process is absent before constructing a new checkpoint. A crash cleanup observation is distinct from an unknown original process-finish timestamp. Unproven POSIX crash cleanup remains blocked rather than implying native qualification.

No checkpoint serializes an external model's hidden reasoning, inference memory, attention state or partial generation. Browser leases and workspace layout are not process checkpoints. This is logical reconstruction from durable application/Git evidence, with existing OS and filesystem race limitations; it is not arbitrary external-side-effect exactly-once execution.

Checkpoint/task/conversation retention is local to the owning project. There is no automatic deletion of mission evidence. Reaching a storage bound requires intervention. To remove an entire disposable project, first stop its active runtime and preserve any desired Git/database evidence, then use the existing project unregister workflow and remove only the explicitly chosen project directory. Presence audit expiry is separate from mission-history retention. There is no checkpoint-pruning API in P10.

Concurrent suspension finalizers reuse one generation-scoped checkpoint only when identity, plan, Git head and worktree fingerprints match; they do not append duplicate checkpoint or state events. Resume commit rechecks session-open state inside the same transaction. A newer suspension can fence an in-progress reconciliation, preventing its older resume commit. No-op suspend requests do not create command history; new resumes stop at 1023 retained commands/run, reserving the next safety-suspension slot. History is not pruned automatically.


## P11 project memory integration

P11 stores no memory-content cache in a mission checkpoint. Manual P10 resume is unchanged. A newly dispatched invocation retrieves eligible current records and audits their revisions; earlier attempts remain historical evidence. Deletion while suspended cannot repopulate prompts from a checkpoint. See [memory governance](memory-governance.md).
