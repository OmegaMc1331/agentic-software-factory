# Browser presence (P10)

Rust owns browser-client leases independently of workspace views, SSE subscribers and agent sessions. The V2 workspace registers a random `bc_` identity for each loaded application instance. Reloading creates a new identity; another valid client prevents absence while the old lease expires. No visibility, focus, editor, project, Dockview or presentation-tab event releases presence. `beforeunload` and `pagehide` retain P04 draft-saving semantics only.

Authenticated registration returns a random `bl_` lease, generation, ordered heartbeat sequence, expiry and server-selected heartbeat interval. The lease is bound to a hash of the validated browser authentication session, the client identity and explicit `(project_id, workspace_session_id)` bindings. It is not a bearer authentication credential. Host, Origin, session and mutation CSRF checks apply. A renewal must match identity/generation and increment sequence by one; an identical sequence acknowledges the previous renewal without extending it. Expired/released leases cannot be renewed. The UI obtains a new lease after an expiration or server restart.

The existing session issuer preserves an already valid signed session token, so another tab refreshing authentication does not change every client's owner identity. Expiration still follows the original signed issue time. After authentication expires, ordinary authenticated registration establishes new presence.

`ASF_BROWSER_LEASE_SECONDS` defaults to 180, accepts 5–3600; `ASF_BROWSER_GRACE_SECONDS` defaults to 60, accepts 0–600. Invalid values refuse application startup. The heartbeat is one sixth of the lease, bounded to 1–30 seconds. Short values are intended for controlled qualification. Production defaults allow ordinary background timer throttling; they are not guarantees against frozen pages, laptop sleep, long network outages or arbitrary browser scheduling.

One application timer checks leases and open project contexts every second. Live expiration and absence grace use `Instant`; wall-clock timestamps describe audit observations. A session with at least one valid explicitly bound client remains present. When none remains, a session-scoped grace timer begins. Reconnection inside grace clears it. Expiration proves missing recent authenticated presence, not physical browser closure. Browser freezes and sufficiently long outages can cause the same safe suspension policy. Chromium's documented [background timer behavior](https://developer.chrome.com/blog/timer-throttling-in-chrome-88/) informed these defaults; native browser evidence remains separate.

Presence audit metadata lives beside the application registry in `*.presence.sqlite3`, schema version 1, WAL with a five-second busy bound. Only authentication hashes are retained, never cookies or CSRF tokens. Startup invalidates old live leases; persisted wall-clock expiry never authorizes new execution. There are at most 256 active leases, 4096 retained in-process lease objects and 10000 audit rows. Expired audit metadata has a seven-day retention policy. Heartbeat persistence failure is not a successful renewal. Lifecycle/presence handlers share a 16-request admission limit; bodies are bounded.

Mission data and checkpoints remain in each project's SQLite database. Legacy CLI and V1 workflows without explicit browser ownership retain their existing lifecycle. The eligible presence client is the production V2 workspace with acknowledged bindings; opening an unrelated legacy page does not silently acquire a workspace session.

See [session ownership](session-lifecycle.md), [suspension](mission-suspension.md) and [checkpoint validation](checkpoint-and-resume.md).

The final absence decision rechecks leases immediately before committing the durable scheduling fence. A returning heartbeat cannot be missed by an older presence snapshot. A project with unavailable or corrupt lifecycle data does not prevent other open projects from enforcing their own absence policy; its own state requires recovery and is never labelled safely suspended.
